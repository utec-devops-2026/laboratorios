# 📘 MLOps Workflow: Data Processing desde Notebook a Script

## 🌐 ¿Cómo ve cada rol los datos?

Imagina que formas parte de un equipo multifuncional. Todos trabajan con los mismos datos, pero desde perspectivas distintas:

- 👷‍♂️ **DevOps Engineer**: piensa en almacenamiento escalable, confiable e infraestructura. Se pregunta: ¿cómo aprovisiono esto con Terraform? ¿cómo lo monitoreo?
- 🧹 **Data Engineer (tú)**: se enfoca en limpiar, procesar, validar y dejar todo listo para otros roles.
- 🔬 **Data Scientist**: ve los datos como un tesoro. Quiere analizarlos y entrenar modelos predictivos.

---

## 🧑‍💻 ¿Qué hace un Ingeniero de Datos?

Tu misión aquí es **garantizar la calidad de los datos**. Recuerda: un modelo no puede ser mejor que los datos que recibe.

### 🛠️ Responsabilidades clave

- Descubrir y reunir datos de múltiples fuentes (transacciones, logs, APIs, Kaggle).
- Procesarlos para que sean consistentes, completos y útiles:
  - Detectar y eliminar duplicados.
  - Corregir tipos de datos.
  - Eliminar valores inválidos o extremos.
  - Validar reglas lógicas (ej. que el precio sea mayor a 0).

### 🧠 Ejemplo de contenido del script:

```python
# run_processing.py
import pandas as pd
import numpy as np

# 1. Cargar datos
raw = pd.read_csv(input_file)

# 2. Eliminar duplicados
data = raw.drop_duplicates()

# 3. Imputar nulos: mediana en numéricas, moda en categóricas
for col in data.columns:
    if data[col].isnull().any():
        if pd.api.types.is_numeric_dtype(data[col]):
            data[col] = data[col].fillna(data[col].median())
        else:
            data[col] = data[col].fillna(data[col].mode()[0])

# 4. Eliminar valores negativos (solo se revisan las columnas numéricas)
num_cols = data.select_dtypes(include=[np.number]).columns
data = data[(data[num_cols] >= 0).all(axis=1)]

# 5. Eliminar outliers del precio con la regla IQR
q1, q3 = data['price'].quantile([0.25, 0.75])
iqr = q3 - q1
data = data[data['price'].between(q1 - 1.5 * iqr, q3 + 1.5 * iqr)]

# 6. Limpiar nombres de columnas
data.columns = data.columns.str.lower().str.replace(' ', '_')

# 7. Guardar datos limpios
data.to_csv(output_file, index=False)
```

> ⚠️ **Ojo con el filtro de negativos.** Una versión anterior de esta guía usaba
> `data[data.select_dtypes(include=[np.number]) >= 0].dropna()`. Esa máscara solo cubre las columnas numéricas,
> así que pandas pone `NaN` en las de texto (`location`, `condition`) y el `dropna()` **borra todas las filas**.
> La forma correcta es filtrar filas con `(data[num_cols] >= 0).all(axis=1)`.

> ⚙️ Este script automatiza todo lo que descubriste en el análisis exploratorio.

## 📜 Paso 2.5: Data contract y gate de validación

Limpiar no es lo mismo que **garantizar**. `run_processing.py` corrige lo que encuentra, pero nadie comprueba que el
resultado cumple lo que el resto del pipeline asume (columnas, tipos, rangos, categorías). Ese acuerdo escrito se llama
**data contract**, y el script que lo verifica es el **primer gate** del pipeline: si falla, nada más se ejecuta.

| Pieza | Archivo | Rol |
|---|---|---|
| Contrato | `src/data/contract.py` | define qué datos son válidos (una sola fuente de verdad) |
| Gate | `src/data/validate.py` | lo aplica y termina con código 1 si hay violaciones |

El mismo contrato se reutiliza más adelante: en el monitoreo (guía 7) para revisar lotes de producción y en el juez de
los PRs del agente (guía 10).

### 🧾 `src/data/contract.py`

```python
"""Data contract del dataset de precios de casas.

El contrato es el acuerdo escrito de cómo se ven los datos válidos. Lo usan:
- src/data/validate.py, como gate del pipeline (si falla, el pipeline se detiene);
- src/monitoring/monitor.py, para revisar los lotes de producción.

Los rangos son deliberadamente amplios: atrapan valores imposibles o errores de
unidades (un área en m² en lugar de ft²), no casas poco comunes pero reales.
"""

from datetime import datetime

import pandas as pd

TARGET = "price"

# columna: (mínimo, máximo)
NUMERIC_BOUNDS = {
    "price": (10_000, 10_000_000),          # USD
    "sqft": (300, 20_000),                  # pies cuadrados; < 300 suele ser un área en m²
    "bedrooms": (1, 10),
    "bathrooms": (0.5, 10),
    "year_built": (1800, datetime.now().year),
}

INTEGER_COLUMNS = ["bedrooms", "year_built"]

CATEGORIES = {
    "location": {"Rural", "Suburb", "Urban", "Downtown", "Waterfront", "Mountain"},
    "condition": {"Poor", "Fair", "Good", "Excellent"},
}

EXPECTED_COLUMNS = ["price", "sqft", "bedrooms", "bathrooms", "location", "year_built", "condition"]


def check_contract(df: pd.DataFrame, require_target: bool = True) -> list[dict]:
    """Devuelve la lista de violaciones del contrato (vacía si los datos son válidos)."""
    expected = EXPECTED_COLUMNS if require_target else [c for c in EXPECTED_COLUMNS if c != TARGET]
    violations = []

    missing = [c for c in expected if c not in df.columns]
    if missing:
        return [{"check": "schema", "column": ", ".join(missing), "rows": len(df),
                 "detail": "faltan columnas obligatorias"}]

    def add(check, column, mask, detail):
        n = int(mask.sum())
        if n:
            violations.append({"check": check, "column": column, "rows": n, "detail": detail})

    for col in expected:
        add("nulls", col, df[col].isnull(), "valores nulos")

    for col, (lo, hi) in NUMERIC_BOUNDS.items():
        if col not in expected:
            continue
        values = pd.to_numeric(df[col], errors="coerce")
        add("type", col, values.isnull() & df[col].notnull(), "no es numérico")
        add("range", col, (values < lo) | (values > hi), f"fuera de [{lo}, {hi}]")

    for col in INTEGER_COLUMNS:
        values = pd.to_numeric(df[col], errors="coerce")
        add("type", col, values.notnull() & (values % 1 != 0), "debería ser entero")

    for col, allowed in CATEGORIES.items():
        add("category", col, df[col].notnull() & ~df[col].isin(allowed), f"fuera de {sorted(allowed)}")

    add("duplicates", "*", df.duplicated(), "filas duplicadas")
    return violations
```

> 💡 Los rangos son amplios a propósito. El contrato no decide qué casa es "rara"; atrapa lo **imposible**:
> un `sqft` de 142 casi seguro es un área en m², una `location` nueva es un cambio de fuente, un nulo es un bug aguas arriba.

### 🧾 `src/data/validate.py`

```python
"""Gate de validación de datos: termina con código 1 si los datos no cumplen el contrato.

Uso:
    python src/data/validate.py --input data/processed/cleaned_house_data.csv
"""

import argparse
import logging
import sys
from pathlib import Path

import pandas as pd

sys.path.insert(0, str(Path(__file__).resolve().parent))
from contract import check_contract  # noqa: E402

logging.basicConfig(level=logging.INFO, format="%(asctime)s - %(name)s - %(levelname)s - %(message)s")
logger = logging.getLogger("data-validation")


def main():
    parser = argparse.ArgumentParser(description="Validate a house-price dataset against the data contract.")
    parser.add_argument("--input", required=True, help="CSV to validate")
    parser.add_argument("--no-target", action="store_true", help="the CSV has no price column (inference batch)")
    args = parser.parse_args()

    df = pd.read_csv(args.input)
    violations = check_contract(df, require_target=not args.no_target)

    if not violations:
        logger.info(f"✅ {args.input}: {len(df)} filas cumplen el data contract")
        return 0

    logger.error(f"❌ {args.input}: {len(violations)} violación(es) del data contract")
    for v in violations:
        logger.error(f"   [{v['check']}] {v['column']}: {v['rows']} fila(s) {v['detail']}")
    return 1


if __name__ == "__main__":
    sys.exit(main())
```

## 🧪 ¿Qué es el EDA?

El **Análisis Exploratorio de Datos (EDA)** es una etapa previa al modelado que permite:

- Entender la **estructura estadística de los datos**
- Visualizar la **distribución de las variables**
- Identificar correlaciones entre atributos
- Detectar sesgos, desbalance o problemas ocultos

El científico de datos recibe los **datos limpios** del ingeniero de datos y explora:

- Valores máximos y mínimos
- Medias, medianas, desviaciones
- Distribución de la variable objetivo
- Relaciones entre columnas

### 4. Correlación entre variables

La matriz de correlación (heatmap) nos permite visualizar rápidamente qué variables numéricas están más relacionadas entre sí. Una correlación cercana a 1 indica una relación lineal directa fuerte, mientras que una correlación cercana a -1 indica una relación inversa. Esto es útil para detectar redundancias (colinealidad) o identificar variables altamente predictivas (como `sqft` y `price`).

```python
plt.figure(figsize=(10, 6))
sns.heatmap(df.corr(), annot=True, cmap="coolwarm")
```

### 5. Relación precio vs pies cuadrados

Este análisis visual muestra cómo se relaciona la superficie de la casa (en pies cuadrados) con su precio. Es común encontrar una **relación lineal positiva**, lo que significa que a mayor superficie, mayor suele ser el precio. El diagrama de dispersión permite ver esa tendencia general, así como posibles valores atípicos o desviaciones que podrían necesitar revisión.

```python
sns.scatterplot(data=df, x="sqft", y="price")
```

### 6. Casas por ubicación (categoría)

```python
df['location'].value_counts().plot(kind="bar")
```

### 7. Precio promedio por número de dormitorios

Este gráfico muestra cómo varía el precio promedio de las viviendas en función del número de dormitorios. Es útil para identificar patrones como: ¿las casas con más dormitorios cuestan sistemáticamente más? ¿Hay un punto donde el precio se estabiliza o incluso baja? Esta observación puede ayudarte a validar hipótesis o ajustar variables categóricas y ordinales.

```python
df.groupby("bedrooms")['price'].mean().plot(kind="bar")
```

## 🎯 ¿Para qué sirve este análisis?

- Detectar **colinealidades** entre variables (ej. sqft y precio)
- Entender **cuáles atributos son más influyentes**
- Saber si se necesitan nuevas features o si las existentes ya explican bien la salida
- Ver si hay **desbalance** entre categorías (ubicaciones poco representadas)

## ⚙️ Paso 3: Automatización del Script en GitHub Actions

Para llevar todo a un entorno real de integración continua, puedes configurar tu flujo de procesamiento de datos como un **workflow automatizado** con GitHub Actions:

### 🧾 `.github/workflows/mlops-pipeline.yml`

```yaml
name: MLOps Pipeline

on:
  workflow_dispatch:
    inputs:
      run_all:
        description: "Run all jobs"
        required: false
        default: "true"

jobs:
  data-processing:
    name: Data Processing
    runs-on: ubuntu-latest

    steps:
      - name: Checkout code
        uses: actions/checkout@v2

      - name: Set up Python
        uses: actions/setup-python@v2
        with:
          python-version: "3.11.9"

      - name: Install dependencies
        run: |
          python -m pip install --upgrade pip
          pip install -r requirements.txt

      - name: Process data
        run: |
          python src/data/run_processing.py --input data/raw/house_data.csv --output data/processed/cleaned_house_data.csv

      # Gate 1: si los datos limpios no cumplen el data contract, el pipeline se detiene aquí
      - name: Validate data contract
        run: |
          python src/data/validate.py --input data/processed/cleaned_house_data.csv
```

> 🚀 Esto permite que el procesamiento de datos se ejecute automáticamente cada vez que lo dispares manualmente o se cree una nueva versión.
